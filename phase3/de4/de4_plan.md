DE4 – BATCH VS STREAMING DATA PROCESSING

Project: Telecom Network Intelligence Pipeline
Phase: Data Engineering
Module: DE4

1. OBJECTIVE

The telecom platform contains workloads with different data-arrival patterns and latency requirements. This section classifies each workload as batch or streaming and explains the appropriate processing approach.

The current project receives daily telecom activity files in CSV format. These files contain historical network activity and are processed as scheduled batch workloads.

Streaming is considered conceptually for future live network-event use cases where information must be processed continuously with low latency.

2. WORKLOAD CLASSIFICATION

Workload 1: Daily Network Summary

Source:
Daily telecom network activity CSV files received through the landing zone.

Arrival pattern:
Daily file arrival.

Latency requirement:
The result is required after the daily files have been received and processed. A target of within 1 hour after the daily input files are available is sufficient.

Processing mode:
BATCH

Reason:
The source data arrives as complete daily files rather than as continuous events. The existing Spark pipeline processes the accumulated daily files efficiently in a scheduled batch.

Batch is appropriate because streaming would add cost without adding value here.

Workload 2: Hypothetical Live Network Events

Source:
Hypothetical live network events generated by network equipment or operational systems.

Arrival pattern:
Continuous event arrival.

Latency requirement:
Seconds to a few minutes.

Processing mode:
STREAMING

Reason:
Events would need to be processed continuously as they arrive. Waiting for a daily batch would introduce unacceptable delay for operational use cases.

v

+------------------+

v                  v

Workload 3: Billing

Source:
Processed network activity and billing-related records.

Arrival pattern:
Periodic billing cycle.

Latency requirement:
Hours to days rather than seconds.

Processing mode:
BATCH

Reason:
Billing does not normally require every event to be processed immediately for the purposes of this project. Periodic aggregation provides sufficient latency while reducing infrastructure complexity.

Batch processing is more appropriate because billing calculations can be performed from accumulated records.

Workload 4: Hotspot Alerts

Source:
Network activity events or continuously updated activity measurements.

Arrival pattern:
Potentially continuous.

Latency requirement:
Seconds to a few minutes.

Processing mode:
STREAMING

Reason:
A hotspot alert is operationally useful only while the high-activity condition is occurring. Streaming processing can evaluate incoming events continuously and trigger an alert without waiting for the next daily batch.

Live Network Events

|
v

Workload 5: Executive Dashboard Refresh

Source:
Curated analytics generated by the telecom processing pipeline.

Arrival pattern:
Daily batch in the current implementation.

Latency requirement:
Within approximately 1 hour after the daily processing run.

Processing mode:
BATCH

Reason:
The current executive dashboard uses aggregated network analytics rather than second-by-second operational events. A scheduled refresh is sufficient for executive reporting.

Batch is appropriate because streaming would add cost without adding value here.

Workload 6: ML Model Training

Source:
Historical processed telecom activity and engineered ML features.

Arrival pattern:
Periodic accumulated training data.

Latency requirement:
Hours.

Processing mode:
BATCH

Reason:
Model training uses historical datasets and does not require continuous event-by-event processing. Training can be scheduled periodically after sufficient new data becomes available.

Batch processing is appropriate because model training is computationally intensive and does not benefit from processing each incoming event independently.

Workload 7: ML Model Scoring

Source:
Engineered network activity features.

Arrival pattern:
Depends on the scoring use case.

Current project:
Batch scoring.

Latency requirement:
Minutes to hours for the current project.

Processing mode:
BATCH

Reason:
The current ML pipeline generates scores from the processed feature dataset rather than requiring continuous event-level decisions. Batch scoring is therefore sufficient for the current implementation.

A future operational version could use streaming scoring if network-risk predictions were required immediately after live events arrived.

6. BATCH VS STREAMING DECISION

Batch processing is selected when:

* Data arrives in complete files or periodic groups.
* Results do not need to be available immediately.
* Processing can be scheduled.
* Historical aggregation is the main requirement.
* Lower infrastructure complexity and cost are preferred.

Streaming processing is selected when:

* Events arrive continuously.
* Results are required within seconds or minutes.
* Operational decisions depend on the latest events.
* Delaying processing until a batch window would reduce business value.

7. WHY THE CURRENT DAILY FILES ARE BATCH

The telecom source files are delivered as daily CSV files.

Each file represents a completed collection of network activity for a defined period. The DE2 ingestion process detects the files, validates them, and routes accepted files to the raw zone. The DE3 Spark pipeline then processes the raw data as a batch.

Therefore:

Daily telecom CSV ingestion = BATCH

It would not be appropriate to describe the current daily CSV ingestion as streaming simply because the underlying telecom activity may have occurred continuously. The important factor is the arrival and processing pattern of the data received by this pipeline.

8. COST AND COMPLEXITY CONSIDERATION

Streaming infrastructure introduces additional operational complexity, including continuous event ingestion, stream-processing infrastructure, monitoring, state management, and failure recovery.

For workloads where a daily or periodic result is sufficient, this additional complexity does not provide meaningful business value.

Therefore, the current project uses batch processing for daily summaries, executive refreshes, billing, ML training, and current ML scoring.

Streaming is reserved conceptually for workloads such as live network events and hotspot alerts where low latency provides direct operational value.

9. FINAL DESIGN DECISION

The telecom platform uses a hybrid conceptual processing strategy:

BATCH:

* Daily network summaries
* Billing
* Executive dashboard refresh
* ML model training
* Current ML model scoring

STREAMING:

* Hypothetical live network events
* Hotspot alerts

The current implemented pipeline remains batch-based because its source data arrives as daily CSV files.

Streaming should be introduced only for use cases where continuous low-latency processing provides measurable value.
